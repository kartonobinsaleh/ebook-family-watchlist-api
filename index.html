Bab 1

Mengenal REST API dan Setup Project

1.1 Apa itu REST API?

Sebelum kita mulai nulis kode, kita perlu sepakat dulu soal apa yang sedang kita bangun.

API adalah singkatan dari Application Programming Interface — sebuah "jembatan" yang memungkinkan dua aplikasi berkomunikasi. Misalnya, aplikasi mobile berkomunikasi dengan server untuk mengambil data.

REST (Representational State Transfer) adalah aturan/gaya arsitektur untuk membuat API. Kalau API kita mengikuti aturan REST, maka disebut REST API atau RESTful API.

Ciri-ciri REST API: - Berkomunikasi lewat HTTP (protokol yang sama dipakai browser) - Data dikirim/diterima biasanya dalam format JSON - Setiap aksi diwakili oleh HTTP Method tertentu (GET, POST, PUT, DELETE) - Tidak ada tampilan — hanya data

Analogi yang mudah diingat:

REST API itu seperti pramusaji di restoran. Kamu (client) memberi tahu pramusaji (API) apa yang kamu mau. Pramusaji mengambilkan dari dapur (server/database), lalu mengantarkan hasilnya ke mejamu. Dapur tidak perlu tahu siapa kamu. Kamu pun tidak perlu masuk ke dapur sendiri.

Ada 4 library di sini. Mari kita kenali satu per satu — bukan asal install, tapi paham dulu fungsinya.

express — Framework Web Server

Express adalah framework untuk membangun web server di Node.js.

Tanpa Express, membuat server HTTP di Node.js itu cukup rumit — kita harus menulis banyak kode manual untuk menangani routing, parsing body, dan sebagainya. Express menyederhanakan semua itu.

Node.js (built-in)    →  Perlu nulis banyak kode manual
Express (di atasnya)  →  Lebih ringkas, mudah dibaca, mudah dipelihara

Kapan dipakai? Dari awal sampai akhir — ini tulang punggung server kita.

helmet — Keamanan HTTP Headers

Helmet adalah library yang menambahkan HTTP response headers secara otomatis untuk melindungi aplikasi dari beberapa serangan web umum.

Kamu mungkin bertanya: "Emangnya apa bahayanya kalau tidak pakai helmet?"

Beberapa serangan yang bisa dicegah: - Clickjacking — website lain bisa menyisipkan halaman kita di dalam iframe tersembunyi untuk menipu pengguna - MIME sniffing — browser menebak-nebak tipe file yang bisa dieksploitasi - Information leakage — header default Express membocorkan info server (X-Powered-By: Express)

Helmet mengaktifkan proteksi-proteksi ini dengan satu baris kode. Mudah dan penting.

Kapan dipakai? Langsung di awal saat setup server.

bcryptjs — Hashing Password

bcrypt adalah algoritma hashing yang dirancang khusus untuk menyimpan password dengan aman.

Kamu pasti sudah pernah dengar: "Jangan simpan password dalam bentuk polos!" Nah, bcrypt adalah solusinya.

Kita tidak akan pakai bcrypt dulu di bab ini. Kita akan mempelajari konsepnya secara mendalam di Bab 3, lalu baru mengimplementasikannya di sana.

jsonwebtoken — Token Autentikasi

JWT (JSON Web Token) adalah standar untuk membuat "kartu identitas digital" yang bisa diverifikasi keasliannya.

Setelah pengguna login, server memberikan JWT. Pengguna menyertakan JWT ini di setiap request berikutnya — seperti menunjukkan kartu identitas setiap kali masuk ke gedung.

Sama seperti bcrypt, kita tidak akan pakai JWT dulu. Kita pelajari konsepnya di Bab 4, lalu implementasi di bab yang sama.

Kenapa tidak langsung pakai semua dari awal?

Karena kalau semua langsung disatukan, kamu akan bingung: mana kode untuk logika bisnis, mana kode untuk keamanan. Kita bangun lapisan demi lapisan agar pemahaman kamu solid.

Kenapa tidak tulis langsung di kode?

// ❌ Cara yang kurang baik
app.listen(3000);

// ✅ Cara yang lebih baik

Dengan process.env.PORT, nilai dibaca dari environment. Di production, PORT bisa berbeda-beda tergantung konfigurasi server. Dan yang paling penting: file .env tidak perlu di-commit ke Git (masukkan ke .gitignore) sehingga secret key tidak bocor ke publik.

Memahami index.js

File index.js adalah pintu masuk aplikasi. Ini yang pertama dijalankan ketika server dinyalakan:

File:index.js
terminal
import express from "express";
import helmet from "helmet";

import watchlistRoutes from "./routes/watchlist.js";

const PORT = process.env.PORT;
const app = express();

// Middleware keamanan HTTP headers
app.use(helmet());

// Middleware agar Express bisa membaca body JSON dari request
app.use(express.json());

// Route untuk cek server aktif
app.get("/", (req, res) => {
  res.send("Family Movie Watchlist API");
});

// Semua route watchlist diakses dengan prefix /api/watchlist
app.use("/api/watchlist", watchlistRoutes);

// Jalankan server
app.listen(PORT, () => {
  console.log(`Server running on port ${PORT}...`);
});

Penjelasan baris penting:

app.use(express.json()) — Middleware ini mengubah body request dari teks mentah menjadi objek JavaScript. Tanpa ini, req.body akan selalu undefined saat client mengirim data JSON.

app.use("/api/watchlist", watchlistRoutes) — Me-mount semua route dari file routes/watchlist.js ke path /api/watchlist. Artinya route /:userId di dalam file tersebut akan diakses sebagai /api/watchlist/:userId.

Jalankan Server

npm start

Kalau berhasil:

Server running on port 3000...

Buka browser dan akses http://localhost:3000 — seharusnya muncul teks "Family Movie Watchlist API". ✅

Bab 2

CRUD Watchlist: Logika Bisnis Pertama Kita

2.1 Apa itu CRUD?

CRUD adalah singkatan dari empat operasi dasar dalam pengelolaan data:

Singkatan Operasi HTTP Method Contoh di project kita
Create Tambah data baru POST Tambah film baru ke watchlist
Read Baca / ambil data GET Lihat daftar film
Update Ubah data yang ada PUT Tandai film sebagai sudah ditonton
Delete Hapus data DELETE Hapus film dari watchlist

Hampir semua aplikasi — dari to-do list sederhana sampai platform e-commerce besar — pada dasarnya adalah CRUD yang dibalut dengan logika bisnis.

2.2 Merencanakan Endpoint

Sebelum menulis kode, rencanakan endpoint terlebih dahulu. Ini yang akan kita buat:

Method Endpoint Deskripsi
GET /api/watchlist/:userId Lihat semua film di watchlist milik user
POST /api/watchlist/:userId/movies Tambah film baru ke watchlist user
PUT /api/watchlist/:userId/movies/:movieId Update data film tertentu
DELETE /api/watchlist/:userId/movies/:movieId Hapus film tertentu dari watchlist

Mengapa POST, PUT, DELETE menggunakan /movies di path-nya?

Ini adalah konvensi REST yang baik. Dengan /movies, endpoint kita jadi lebih deskriptif dan jelas:

/api/watchlist/1          → Resource: watchlist milik user 1
/api/watchlist/1/movies   → Resource: koleksi film dalam watchlist user 1
/api/watchlist/1/movies/2 → Resource: film ke-2 dalam watchlist user 1

URL yang baik harus self-documenting — orang yang membacanya langsung mengerti tanpa perlu penjelasan tambahan.

Apa itu :userId dan :movieId?

Itu disebut URL Parameter — bagian URL yang nilainya dinamis. Tanda : menandakan variabel:

GET /api/watchlist/1   → userId = "1" (Dad Miller)
GET /api/watchlist/3   → userId = "3" (Jake Miller)

2.5 Membuat Routes Watchlist

Buat file baru: routes/watchlist.js

File:routes/watchlist.js
json
import express from "express";
import {
  getWatchlist,
  addMovie,
  updateMovie,
  deleteMovie,
} from "../utils/db.js";

const router = express.Router();

// ─────────────────────────────────────────
// GET /api/watchlist/:userId
// Mengambil semua film dalam watchlist milik seorang user
// ─────────────────────────────────────────
router.get("/:userId", (req, res) => {
  const userId = Number(req.params.userId);

  const watchlist = getWatchlist(userId);

  if (watchlist === null) {
    return res.status(404).json({ error: "User not found" });
  }

  res.json(watchlist);
});

// ─────────────────────────────────────────
// POST /api/watchlist/:userId/movies
// Menambahkan film baru ke watchlist user
// ─────────────────────────────────────────
router.post("/:userId/movies", (req, res) => {
  const userId = Number(req.params.userId);
  const { title, genre } = req.body;

  if (!title || !genre) {
    return res.status(400).json({ error: "title and genre are required" });
  }

  const movie = addMovie(userId, { title, genre });

  if (movie === null) {
    return res.status(404).json({ error: "User not found" });
  }

  res.status(201).json(movie);
});

// ─────────────────────────────────────────
// PUT /api/watchlist/:userId/movies/:movieId
// Mengupdate data film (misalnya menandai sudah ditonton)
// ─────────────────────────────────────────
router.put("/:userId/movies/:movieId", (req, res) => {
  const userId = Number(req.params.userId);
  const movieId = Number(req.params.movieId);
  const updates = req.body;

  const updated = updateMovie(userId, movieId, updates);

  if (updated === null) {
    return res.status(404).json({ error: "Movie or user not found" });
  }

  res.json(updated);
});

// ─────────────────────────────────────────
// DELETE /api/watchlist/:userId/movies/:movieId
// Menghapus film dari watchlist
// ─────────────────────────────────────────
router.delete("/:userId/movies/:movieId", (req, res) => {
  const userId = Number(req.params.userId);
  const movieId = Number(req.params.movieId);

  const result = deleteMovie(userId, movieId);

  if (result === null) {
    return res.status(404).json({ error: "Movie or user not found" });
  }

  res.json({ message: "Movie deleted successfully" });
});

export default router;

Hal penting yang perlu diperhatikan:

Number(req.params.userId) — Parameter URL selalu berupa string. ID di data kita berupa angka. Kalau tidak dikonversi, perbandingan "1" === 1 menghasilkan false dan pencarian akan selalu gagal.

HTTP Status Code — Bukan sekadar formalitas:

Kode Nama Kapan digunakan
200 OK Request berhasil (default GET, PUT, DELETE)
201 Created Data baru berhasil dibuat (POST)
400 Bad Request Input dari client salah atau kurang
404 Not Found Data yang dicari tidak ada

Bab 3

Keamanan Password: Kenalan dengan bcrypt

3.1 Bahaya Menyimpan Password Polos

Sebelum kita tambahkan fitur login, ada satu hal yang harus kita pahami benar-benar dulu.

Bayangkan kita menyimpan password seperti ini di database:

json
{
  "username": "dad_miller",
  "password": "parent456"
}

Ini disebut menyimpan password dalam bentuk plaintext (teks polos). Dan ini adalah praktik yang sangat berbahaya.

Kenapa berbahaya?

Bayangkan skenario ini: suatu hari server kamu diretas, dan penyerang berhasil mengakses database. Semua password langsung terbaca tanpa perlu usaha apapun.

Yang lebih parah lagi, penelitian menunjukkan bahwa lebih dari 50% pengguna menggunakan password yang sama di berbagai layanan — email, rekening bank, media sosial. Satu kebocoran bisa jadi petaka berantai bagi penggunamu.

"Tapi kalau serverku sudah diproteksi dengan baik, tidak akan ada yang bisa masuk!"

Tidak ada sistem yang 100% aman. Pendekatan terbaik adalah defense in depth — bahkan kalau satu lapisan pertahanan jebol, lapisan lainnya masih melindungi. Menyimpan password yang sudah di-hash adalah salah satu lapisan penting itu.

3.2 Apa itu Hashing?

Hashing adalah proses mengubah data (misalnya password) menjadi "sidik jari" digital yang panjangnya tetap — dan tidak bisa dikembalikan ke bentuk aslinya.

"parent456"  →  [fungsi hash]  →  "$2a$10$V4nCDj9z1mpYmhilx43xy..."

Ciri-ciri hashing:

  • One-way (satu arah) — Dari hash, tidak bisa mendapatkan teks aslinya. Ini yang membedakannya dari enkripsi yang bisa di-decrypt.
  • Avalanche Effect — Perubahan kecil pada input menghasilkan output yang sama sekali berbeda: "parent456" → "$2a$10$V4nCDj9..." "parent457" → "$2a$10$Xq8pLmK..." ← Sama sekali berbeda!

Kalau tidak bisa di-reverse, bagaimana cara verifikasi password?

Server tidak perlu mendekripsi hash. Yang dilakukan adalah: hash ulang password yang diinput user, lalu bandingkan hasilnya dengan hash di database. Kalau cocok → password benar.

User input: "parent456"
                ↓ [hash ulang]
            "$2a$10$V4nCDj9..."
                ↓ [bandingkan]
            "$2a$10$V4nCDj9..." ← dari database
                ↓
              COCOK ✅ → Login berhasil

3.3 Kenapa Harus bcrypt?

Kamu mungkin pernah dengar tentang algoritma hash lain seperti MD5 atau SHA256. Kenapa tidak pakai itu saja?

Jawabannya adalah: MD5 dan SHA256 dirancang untuk kecepatan. Mereka bisa memproses miliaran hash per detik menggunakan GPU modern. Penyerang bisa mencoba semua kombinasi password umum dalam hitungan detik — ini disebut brute force atau dictionary attack.

bcrypt dirancang untuk lambat — dan itu justru kelebihannya untuk hashing password.

bcrypt punya cost factor yang menentukan seberapa banyak iterasi hashing dilakukan:

Cost 10  →  ~100ms per hash  →  sangat lambat bagi penyerang
Cost 12  →  ~400ms per hash  →  lebih lambat lagi

Bagi pengguna yang login, keterlambatan 100ms tidak terasa. Tapi bagi penyerang yang ingin mencoba jutaan kombinasi? Ini hambatan yang sangat besar.

Struktur Hash bcrypt:

$2a$10$V4nCDj9z1mpYmhilx43xy.Wl9whaKMmSMSpL4qXmrS.Z73JSq7vRe
 ↑   ↑  ↑─────────────────────────────────────────────────────↑
 │   │                    Salt + Hash (53 karakter)
 │   └── Cost Factor (10)
 └─────── Versi algoritma bcrypt

Yang menarik: hash bcrypt sudah berisi semua informasi untuk verifikasi — versi, cost factor, dan salt. Kita tidak perlu menyimpan salt secara terpisah.

3.4 Implementasi Login dengan bcrypt

Sekarang kita buat endpoint login yang menggunakan bcrypt untuk memverifikasi password.

Buat file baru: routes/auth.js

File:routes/auth.js
import express from "express";
import bcrypt from "bcryptjs";
import { findByUsername } from "../utils/db.js";

const router = express.Router();

// ─────────────────────────────────────────
// POST /api/auth/login
// ─────────────────────────────────────────
router.post("/login", async (req, res) => {
  const { username, password } = req.body;

  // 1. Validasi input: kedua field wajib diisi
  if (!username || !password) {
    return res.status(400).json({ error: "Username and password are required" });
  }

  // 2. Cari user berdasarkan username
  const user = findByUsername(username);
  if (!user) {
    // Jangan tulis "Username tidak ditemukan" — itu membocorkan informasi!
    return res.status(401).json({ error: "Invalid credentials" });
  }

  // 3. Verifikasi password menggunakan bcrypt
  const isPasswordValid = await bcrypt.compare(password, user.passwordHash);
  if (!isPasswordValid) {
    return res.status(401).json({ error: "Invalid credentials" });
  }

  // 4. Login berhasil — untuk saat ini, kembalikan info user
  //    (token JWT akan kita tambahkan di Bab 4)
  res.json({
    message: "Login successful",
    user: {
      id: user.id,
      name: user.name,
      username: user.username,
      role: user.role,
    },
  });
});

export default router;

Kenapa async/await?

bcrypt.compare() adalah operasi yang memakan waktu CPU (karena sengaja lambat). Dengan async/await, server tidak "membekukan" saat memproses satu request — server tetap bisa melayani request lain dari user yang berbeda.

Kenapa error message-nya "Invalid credentials" bukan lebih spesifik?

Pesan yang terlalu spesifik seperti "Username tidak ditemukan" membantu penyerang mengetahui apakah sebuah username valid atau tidak — ini disebut user enumeration attack. Kita samarkan keduanya dengan pesan yang sama agar penyerang tidak mendapat informasi berharga.

Bab 4

Autentikasi: Kenalan dengan JWT

4.1 Masalah HTTP yang Stateless

HTTP adalah protokol yang stateless — setiap request yang masuk ke server dianggap sebagai request baru yang independen. Server tidak menyimpan "ingatan" tentang siapa yang sudah login.

Analogi:

Bayangkan kamu masuk ke sebuah gedung yang dijaga satpam. Satpam itu punya penyakit aneh — dia kehilangan memori setiap beberapa detik. Setiap kali kamu melewati pintu, dia tidak mengenalimu dan meminta kamu menunjukkan identitas lagi dari awal.

Itulah HTTP. Server adalah satpam yang pelupa.

Solusi lama: Session

Server menyimpan data "siapa yang sudah login" di memory, lalu memberikan "tiket" (session ID) kepada client. Client menyertakan tiket ini di setiap request. Server mengecek tiket ke penyimpanannya.

Masalahnya: kalau kamu punya banyak server (untuk melayani jutaan pengguna), semua server perlu berbagi data session yang sama. Ini rumit dan tidak scalable.

Solusi modern: Token (JWT)

Server memberikan "kartu identitas digital" kepada client setelah login. Client menyertakan kartu ini di setiap request. Server hanya perlu memverifikasi kartu — tidak perlu menyimpan apapun di sisi server.

4.2 Apa itu JWT?

JWT (JSON Web Token) adalah standar terbuka untuk membuat token yang berisi informasi dan bisa diverifikasi keasliannya.

Sebuah JWT terdiri dari tiga bagian yang dipisahkan oleh tanda titik (.):

eyJhbGciOiJIUzI1NiJ9.eyJpZCI6MSwicm9sZSI6InBhcmVudCJ9.abc123xyz
       ↑                          ↑                          ↑
    HEADER                     PAYLOAD                   SIGNATURE

Header — Jenis token dan algoritma:

{ "alg": "HS256", "typ": "JWT" }

Payload — Data yang ingin kita simpan di dalam token:

json
{
  "id": 1,
  "username": "dad_miller",
  "role": "parent",
  "iat": 1700000000,
  "exp": 1700086400
}

iat = issued at — kapan token dibuat exp = expiration — kapan token kadaluarsa

Signature — Tanda tangan digital:

HMACSHA256(
  base64(header) + "." + base64(payload),
  SECRET_KEY
)

⚠️ Penting untuk Dipahami!

Bagian Header dan Payload JWT hanya di-encode dengan Base64 — artinya, siapapun bisa membacanya. JWT bukan enkripsi!

Tapi tidak ada yang bisa mengubah isinya tanpa merusak Signature — karena Signature dibuat menggunakan secret key yang hanya server yang tahu.

Kesimpulan: Jangan simpan password atau data sangat sensitif di dalam JWT payload.

4.3 Cara Kerja JWT dalam Autentikasi

json
Client                                    Server
  │                                         │
  │  POST /api/auth/login                   │
  │  { username, password }                 │
  │ ───────────────────────────────────►   │
  │                                         │  1. Verifikasi credentials
  │                                         │  2. Buat JWT berisi { id, role }
  │  { token: "eyJ..." }                   │
  │ ◄───────────────────────────────────   │
  │                                         │
  │  [simpan token di client]               │
  │                                         │
  │  GET /api/watchlist/1                   │
  │  Authorization: Bearer eyJ...           │
  │ ───────────────────────────────────►   │
  │                                         │  3. Verifikasi JWT (tanpa DB!)
  │                                         │  4. Tahu siapa user-nya dari token
  │  [data watchlist]                       │
  │ ◄───────────────────────────────────   │

Setelah mendapatkan token, client menyertakannya di header setiap request dengan format:

Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...

4.4 Implementasi JWT di Login

Pertama, tambahkan JWT_SECRET ke file .env:

File:.env
PORT=3000
JWT_SECRET=ini-adalah-secret-key-yang-panjang-dan-sangat-rahasia-minimal-32-karakter

Kenapa JWT_SECRET harus panjang dan acak?

Secret key digunakan untuk membuat dan memverifikasi signature. Kalau mudah ditebak (seperti "secret" atau "abc123"), penyerang bisa membuat token palsu. Gunakan minimal 32 karakter acak di production.

Update routes/auth.js — tambahkan pembuatan JWT:

File:routes/auth.js
import express from "express";
import bcrypt from "bcryptjs";
import jwt from "jsonwebtoken";      // ← Tambahkan
import { findByUsername } from "../utils/db.js";

const router = express.Router();
const JWT_SECRET = process.env.JWT_SECRET;  // ← Tambahkan

router.post("/login", async (req, res) => {
  const { username, password } = req.body;

  if (!username || !password) {
    return res.status(400).json({ error: "Username and password are required" });
  }

  const user = findByUsername(username);
  if (!user) {
    return res.status(401).json({ error: "Invalid credentials" });
  }

  const isPasswordValid = await bcrypt.compare(password, user.passwordHash);
  if (!isPasswordValid) {
    return res.status(401).json({ error: "Invalid credentials" });
  }

  // ── Buat JWT Token ────────────────────────────────────────
  const token = jwt.sign(
    {
      id: user.id,           // ← ID user (number)
      username: user.username,
      role: user.role,       // ← "parent" atau "child"
    },
    JWT_SECRET,              // ← Secret key untuk tanda tangan
    { expiresIn: "1h" }      // ← Token kadaluarsa dalam 1 jam
  );
  // ─────────────────────────────────────────────────────────

  res.json({
    message: "Login successful",
    token,   // ← Kirim token ke client
  });
});

export default router;

Mengapa response hanya mengembalikan token?

FreeCodeCamp mensyaratkan response memiliki field token. Kalau ingin tambahkan info user juga, boleh — tapi field token wajib ada.

4.5 Membuat Middleware authenticate

Sekarang kita buat middleware yang bertugas memeriksa token JWT di setiap request.

Apa itu Middleware?

Middleware adalah fungsi yang berjalan di "tengah-tengah" antara request masuk dan route handler. Seperti pos pemeriksaan — setiap request harus melewati pos ini sebelum bisa lanjut.

Request → [authenticate] → [Route Handler] → Response
                ↓ (kalau token tidak valid)
           401 Unauthorized

Fungsi middleware punya tiga parameter: req, res, dan next. Fungsi next() digunakan untuk meneruskan ke middleware atau route handler berikutnya.

Buat file baru: middleware/authenticate.js

File:middleware/authenticate.js
import jwt from "jsonwebtoken";

const JWT_SECRET = process.env.JWT_SECRET;

export function authenticate(req, res, next) {
  // 1. Ambil header Authorization
  //    Format yang diharapkan: "Bearer eyJhbGciOiJIUzI1NiJ9..."
  const authHeader = req.headers["authorization"];
  const token = authHeader && authHeader.split(" ")[1];

  // 2. Kalau tidak ada token, tolak dengan 401
  if (!token) {
    return res.status(401).json({ error: "No token provided." });
  }

  // 3. Verifikasi token
  try {
    const decoded = jwt.verify(token, JWT_SECRET);
    req.user = decoded;  // ← Simpan info user ke dalam request
    next();              // ← Lanjutkan ke handler berikutnya
  } catch (err) {
    // Token tidak valid atau sudah kadaluarsa
    return res.status(401).json({ error: "Invalid or expired token." });
  }
}

Perhatikan dua hal penting:

  1. Pesan error harus tepat — termasuk tanda titik (.) di akhir: - Tidak ada token → "No token provided." (status 401) - Token tidak valid → "Invalid or expired token." (status 401)

  2. Keduanya menggunakan status 401 — Baik "tidak ada token" maupun "token tidak valid" sama-sama berarti request tidak terautentikasi. Kita tidak perlu membedakan keduanya dengan status code yang berbeda dari sudut pandang client.

Mengapa kita simpan decoded token ke req.user?

req adalah objek yang merepresentasikan HTTP request. Kita bisa menambahkan properti kustom ke objek ini untuk diteruskan ke handler berikutnya. Dengan menyimpan decoded ke req.user, route handler selanjutnya bisa tahu siapa yang melakukan request tanpa perlu decode token lagi.

Bab 5

Otorisasi: Siapa Boleh Melakukan Apa?

5.1 Autentikasi vs Otorisasi

Dua konsep ini sering tertukar. Tapi bedanya sangat fundamental:

Autentikasi Otorisasi
Pertanyaan "Siapa kamu?" "Apa yang boleh kamu lakukan?"
Tujuan Membuktikan identitas Memberikan/menolak hak akses
Tools bcrypt + JWT Role check, permission check
Status error 401 Unauthorized 403 Forbidden

Analogi Hotel:

  • Autentikasi: Resepsionis memverifikasi identitasmu saat check-in, lalu memberikan kunci kamar.
  • Otorisasi: Kunci kamar 101 hanya bisa membuka kamar 101. Tidak bisa membuka kamar 202, tidak bisa masuk ke ruang server hotel.

Jadi autentikasi menjawab siapa, otorisasi menjawab boleh tidak.

Penting:

Autentikasi tanpa otorisasi berarti semua pengguna yang sudah login bisa melakukan apapun. Seperti hotel yang memberikan kunci master kepada semua tamu — tidak masuk akal!

5.2 Role-Based Access Control (RBAC)

RBAC (Role-Based Access Control) adalah pendekatan otorisasi yang paling umum. Setiap pengguna memiliki role (peran), dan setiap role memiliki hak akses yang berbeda.

Di project kita, ada dua role: - parent — Bisa melakukan modifikasi (tambah/ubah/hapus) ke watchlist siapapun - child — Hanya bisa memodifikasi watchlist milik sendiri

Aturan untuk endpoint modifikasi (POST, PUT, DELETE):

Siapa Akses ke watchlist sendiri Akses ke watchlist orang lain
parent ✅ Boleh ✅ Boleh
child ✅ Boleh ❌ Ditolak (403)

Bagaimana dengan endpoint GET?

Untuk endpoint GET (melihat watchlist), aturannya berbeda — semua user yang sudah login bisa melihat watchlist siapapun, terlepas dari role-nya. Kita tidak memasang otorisasi di GET.

Ini adalah keputusan desain yang disengaja. Dalam konteks keluarga, wajar kalau semua anggota bisa melihat film apa yang ditonton orang lain — tapi hanya parent yang bisa memodifikasi watchlist orang lain.

5.3 Membuat Middleware authorizeModification

Buat file baru: middleware/authorize.js

File:middleware/authorize.js
javascript
export function authorizeModification(req, res, next) {
  const role = req.user.role;
  const loggedInUserId = req.user.id;           // ← number (dari JWT payload)
  const requestedUserId = Number(req.params.userId); // ← konversi dari string ke number

  // Parent boleh memodifikasi watchlist siapapun → langsung lanjut
  if (role === "parent") {
    return next();
  }

  // Child hanya boleh memodifikasi watchlist milik sendiri
  if (role === "child" && loggedInUserId === requestedUserId) {
    return next();
  }

  // Selain itu → tolak
  return res.status(403).json({ error: "Access denied" });
}

Kenapa kita perlu Number(req.params.userId)?

req.params.userId adalah string (misalnya "3"), sedangkan req.user.id yang kita simpan di JWT adalah angka (misalnya 3). Perbandingan "3" === 3 menghasilkan false! Kita harus mengkonversi salah satunya agar perbandingan berjalan benar.

Kenapa pesan error-nya hanya "Access denied"?

Sederhana dan tidak membocorkan informasi. Penyerang tidak perlu tahu mengapa mereka ditolak — apakah karena role salah, atau karena ID tidak cocok.

Langkah Selanjutnya

Kamu sudah menyelesaikan project ini dan paham mengapa setiap bagiannya ada. Beberapa topik yang bisa kamu eksplorasi selanjutnya:

  • Database nyata — Ganti file JSON dengan PostgreSQL menggunakan Prisma ORM
  • Refresh Token — JWT kadaluarsa dalam 1 jam. Bagaimana memperbaruinya tanpa login ulang?
  • Rate Limiting — Batasi jumlah login attempt untuk mencegah brute force
  • Input Validation — Gunakan library zod untuk validasi input yang lebih robust
  • Unit Testing — Test setiap endpoint dengan Jest atau Vitest
